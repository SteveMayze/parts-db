# ADR 0002: Fresh rootless Podman deployment under `homeapps`, with persistent data and media folders

Status: accepted (phase R1, 2026-11-01, design only; nothing is deployed yet). Partly supersedes ADR 0001 (see its marked lines). Based on the Tax app's ADR 0007 (`SteveMayze/Tax-and-KK-Tool`, `docs/decisions/0007-rootless-podman.md`), reduced to what this smaller app needs.

## Context
parts-db ran as a rootful system Quadlet unit, deployed with sudo, publishing `8888:8000` on all interfaces. Inspection of the running rootful container showed that the PDF folder was **never a mounted directory**: the unit mounted only the database file and `staticfiles`, so uploaded PDFs lived in the container's writable layer and were destroyed at every redeploy. Of 38 purchase documents, all 38 had lost their PDF original. The owner decided that the existing data is **not** worth migrating and will reload it through the app's imports (CSV and PDF).

Read-only inspection of the server as `homeapps` (2026-11-01): Podman 5.4.2, systemd 257, linger on, the `gateway` network and the Caddy and Tax Quadlet files exist in `~/.config/containers/systemd/`, 19 GB free, ports 8888, 8889, 8890 in use, 8891 free.

## Decisions
1. **No migration.** Nothing is read, copied or compared from the rootful instance. The earlier plan (`migrate-copy`, `verify-migration`, data hashes) is dropped. The rootful instance stays untouched until the owner stops it (documented sudo commands, run by the owner).
2. **Layout** `/home/homeapps/parts-db/{data,media,backups,build,config}`, mode 0700, owned by `homeapps`. `data` holds the SQLite database as a *folder* (SQLite writes journal files beside the file, which a single-file bind mount cannot provide), `media` all PDF originals including `tmp_imports`, `backups` the verified archives, `config/env` the secret key (mode 0600), `build` the unpacked revisions.
3. **Paths from the environment** (defaults unchanged, so development and tests are unaffected): `DJANGO_DB_PATH`, `DJANGO_MEDIA_ROOT`, `DJANGO_BACKUP_DIR`. Also `DJANGO_HTTPS` (Secure cookies) and `DJANGO_HSTS_SECONDS` (stays 0), and a `/health/` endpoint. The flag `DJANGO_BEHIND_TLS_PROXY` now treats `0`/`false`/empty as off (it was "any non-empty value", which would have turned `0` into on).
4. **User mapping** `UserNS=keep-id:uid=10001,gid=10001` with `User=10001`, as in the Tax ADR 0007: the host user `homeapps` appears inside the container as the app user, so the mounted folders need no `chown` and no root.
5. **Hardening:** non-root user in the image, read-only root file system with `Tmpfs=/tmp`, `DropCapability=ALL`, `NoNewPrivileges`, 512 MB memory and 256 process limits, health check (`healthcheck.py`, a script because Quadlet re-quotes inline commands) with `HealthOnFailure=restart`. Static files are collected at image build time, so nothing is written to the image at run time.
6. **Network:** `Network=gateway.network` (created by the gateway repository, joined, never created or changed here), container name `parts-db-web`, port 8000 inside. `PublishPort=127.0.0.1:8891:8000` is for health probes and SSH tunnels only. The plain-HTTP origin `:8888` stays in the CSRF trusted origins until phase R3, and `DJANGO_HTTPS` stays 0 until then (Secure cookies would break the plain port).
7. **Secret:** a **new** Django secret key is generated on the server on the first deploy into `config/env` (0600, `homeapps` only), with `no_log`, never overwritten, never printed. The old key is treated as exposed. Nobody needs it, since the data starts empty.
8. **Deploys** build the image as `homeapps` from `git archive` of the committed revision (uncommitted changes are refused; untracked files can never be shipped). A pre-deploy backup is taken before migrations whenever a database exists. Images are tagged by commit and `current`/`previous`; housekeeping keeps the newest 5 and only ever names `localhost/parts-db`.
9. **Backups:** a systemd *user* timer (daily 03:15, `Persistent=true`) runs `manage.py backup_db --prune`: database via the SQLite online-backup API (never a plain copy of a live file) and the whole media tree in one archive with SHA-256 manifest, integrity check and row counts, re-verified after writing. Retention keeps the newest per day for 14 days, per month for 12 months, labelled backups (pre-deploy, pre-restore, ...) for 30 days, and always the newest backup. `make fetch-backup` copies one to the owner's computer (git-ignored `local/`), `make restore-drill` proves a restore in a throw-away place, `make restore` restores into live data only after the owner types `RESTORE`, takes a safety backup first and moves existing data aside instead of deleting it.
10. **Never delete data:** no `state: absent`, `rsync --delete`, `rm`, or `prune` in the deploy playbooks (a test enforces this). Restore moves instead of deleting.
11. **No bootstrap playbook.** The user, linger, sub-ids and Podman were created by the Tax repository's bootstrap. The deploy only checks them (`infra/tasks/service-session.yml`, the gateway network file) and fails politely without changing anything.
12. **Rollback:** `make rollback` re-tags `previous` as `current` after proving the old image starts with the current configuration; data is untouched unless a backup name is given. Before the gateway switch, rolling back is switching the gateway upstream back (the rootful instance is still running).

## Isolation from the Tax app (stated plainly)
Both apps run as the **same Linux user** `homeapps` and both containers use uid 10001 inside. `keep-id` maps both to the same host user, so a folder mounted into one container would be readable by the other. There is no kernel-level separation between them. The separation is by **naming and by the mount list**: own data root, image repository (`localhost/parts-db`), container (`parts-db-web`), units (`parts-db-web.service`, `parts-db-backup.service/.timer`), env file, secret key, backups and probe port; the container mounts only `parts-db/data`, `parts-db/media` and `parts-db/backups`, never `/home/homeapps` or a Tax path. The only shared object is the `gateway` network. Tests assert that no rendered path, mount, unit, image or container name contains a Tax name, that every mount source is under the parts-db data root, and that the deploy refuses any other `data_root`.

## What needs root, and why
Only stopping (and later removing) the rootful unit, because it is a root-owned system service. Everything else, including deploy, status, backup, restore and rollback, runs as `homeapps`. A test fails if `sudo`, `become` or `-K` appear in the rootless Makefile targets, playbooks or templates.

## Left out compared with the Tax app, and why
`bootstrap-rootless.yml` and `migrate-from-rootful.yaml`/`verify-migration.yaml` (cancelled or already done), the data fingerprint, `stored_files_report`, optional app settings in the env file, a trial port (the rootless copy runs beside the old one on 8891 anyway), and fully pinned requirements and Python patch version (parts-db keeps its existing ranges; pinning is a separate decision).

## Consequences
- The old data is gone. Reloading is done by the owner through the CSV and PDF imports; steps in `docs/deployment.md`.
- The 38 purchase document rows of the old instance whose PDFs were lost are not repaired or carried over.
- The unit generator dry-run, ansible syntax check and the tests prove the files are well-formed; a real start, the gateway reaching the container by name and reboot survival can only be proven on the server (phase R2).
