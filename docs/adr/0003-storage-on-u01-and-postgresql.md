# ADR 0003: Storage on /u01 and PostgreSQL

Status: accepted. Storage moved to /u01 on 2026-11-08 (PD2); PostgreSQL cutover done on 2026-11-08 (PD4). The reboot test after the cutover is still open.

## Context
parts-db runs as the rootless Quadlet container `parts-db-web` of `homeapps`, with SQLite, the PDF originals and the backups under `/home/homeapps/parts-db/{data,media,backups}` on the eMMC (27 GB root partition, 17 GB free). A 1 TB disk is mounted at `/u01`. The platform (`cornil-gateway`) runs a shared PostgreSQL 17 container with the `db` network and the secret `partsdb-db-password`. The shared contract v1 (`docs/prompts/PARTSDB-U01-POSTGRES.md`) fixes the layout, the settings and the unit lines.

Measured on 2026-11-03 (counts and sizes only): data 256 KB, media 1 MB (4 PDFs), backups 4.7 MB; live rows: 1 supplier, 1 user, 0 parts, 8 admin-log entries. The data is tiny, so the migration can be rehearsed cheaply and repeated.

## Decisions (proposed)
1. **Storage.** `data`, `media`, `backups` move to `/u01/data/parts-db`; builds to `/u01/apps/parts-db/build`. `config/env` (Django secret key) stays on the eMMC. Container-side paths do not change. Move by copy and checksum comparison, never by deletion; the old folders stay as rollback until the owner removes them.
2. **Guard.** The unit and the backup service carry `ExecStartPre=/usr/bin/mountpoint -q /u01`, `Restart=on-failure`, `RestartSec=10`, `StartLimitIntervalSec=0`. `RequiresMountsFor=` is not a guard in a user unit.
3. **Database.** PostgreSQL via `DJANGO_DB_HOST` and four more variables; SQLite stays the default when the host is unset (development, tests). Driver `psycopg` 3, pinned. The password arrives only as the Podman secret `partsdb-db-password`.
4. **Migration method.** ORM `dumpdata` / `loaddata` with natural keys, excluding `contenttypes`, `auth.permission` and `sessions` (migrate recreates them), then `sqlsequencereset`. Not `pgloader`: with this schema it adds a tool, type-cast rules and a second code path for no gain. Proof: an engine-neutral `data_fingerprint` command run on both sides.
5. **Backups on PostgreSQL.** The app's own `backup_db` keeps producing one archive holding database and PDFs together: `pg_dump -Fc` plus the media tree, SHA-256 manifest, `pg_restore --list` check, same retention. The platform's nightly dump stays as an independent second layer; it does not hold the PDFs, so it cannot replace the archive.
6. **Ordering.** PostgreSQL sorts text by locale, SQLite by bytes. The parts list sort is done in Python (`_sort_text_key`) and is engine independent; the database orderings (Meta `ordering`, dropdown `order_by`) get an explicit, tested ordering.

7. **How the storage switch is implemented (PD1).** `data_root` (where data, media and backups are *now*) is derived: `storage_root` when `use_u01` is true (the committed default), `legacy_root` (`~/parts-db`) otherwise. `config_root` (secret env file, `DEPLOYED`) never moves. A marker file `config/storage_location` on the server (`u01` or `legacy`) records the real state; `make deploy` refuses before changing anything when it disagrees with `use_u01`, when `/u01` is not a mount point, or when the storage folders are missing or not owned by `homeapps`. `make relocate-storage` stops the app, takes a `pre-relocate` backup, copies with `cp -a` into folders that must be empty, compares file lists and the SHA-256 of every file, shows the result, and switches only after the owner types `SWITCH`; on any failure the app is restarted on the old folders. `make rollback-storage` (confirmation `ROLLBACK`, safety backup first) points the unit back. Nothing is deleted: the old folders remain until the owner removes them. Builds use `/u01/apps/parts-db/build` and `TMPDIR` on `/u01`. The guard lines appear only in the `/u01` layout; the legacy layout renders the old unit.

8. **Settings and driver (PD3).** `DJANGO_DB_HOST` unset: SQLite exactly as before. Set: PostgreSQL from `DJANGO_DB_HOST`, `_PORT` (5432), `_NAME` (`partsdb`), `_USER` (`partsdb`), `_PASSWORD`. `CONN_MAX_AGE=60` with `CONN_HEALTH_CHECKS`, `connect_timeout=5`. Driver `psycopg[binary]==3.3.8`: a wheel with its own libpq exists for CPython 3.12 on Linux, so the image does not need `libpq5`; Django 5.2 supports psycopg 3.1.8 and later.
9. **Image (PD3).** Base `python:3.12-slim-trixie` (Debian 13, as the server), `postgresql-client-17` from Debian's own repository, and a build step that fails if `pg_dump`/`pg_restore` are missing or older than 17. Non-root user, read-only root and dropped capabilities are unchanged. The backup tools must not be older than the server because `pg_dump` refuses a newer server.
10. **Backups on PostgreSQL (PD3).** `backup_db` takes `pg_dump -Fc` from an exported snapshot inside a REPEATABLE READ transaction, and counts rows through the ORM inside that same transaction, so dump and counts describe one moment while the app keeps running. Same file name, retention and manifest (SHA-256 per file, row counts, plus `engine` and `app_version`); verified again after writing with checksums and `pg_restore --list`. Restore goes into a new empty database and compares row counts; swapping needs `--swap --confirm-swap SWAP` and renames the live database aside (`<name>_before_restore_<time>`), never dropping it. The drill creates its own scratch database and is the only thing that ever drops one, and only one it created. Both the swap and the drill need the role to hold `CREATEDB`: an open question for the platform repository (see the PD3 report).
11. **Fingerprint (PD3).** `data_fingerprint` hashes every model in primary-key order in one normalised text form (decimals without trailing zeros, timestamps in UTC, references to content types and permissions by natural key) and prints counts and hashes only. A golden test pins the hashes: the same rows give the same hashes on SQLite and PostgreSQL.
12. **Ordering (PD3).** Everything the user sees in an order is sorted in Python with one key (`parts/ordering.py`: case and accents ignored, digit runs as numbers, ties by raw text, then id): the default parts list, the project list, supplier and project dropdowns, and the type, subtype, packaging and client lists. The `Meta.ordering` options stay (no migration) but nothing displayed relies on them. A test with umlauts, mixed case and numbers passes on both engines.
13. **Deployment switch (PD3).** `use_postgres: false` by default. When true, the unit gets `Network=db.network`, `Wants=` and `After=postgres.service`, `Secret=partsdb-db-password,type=env,target=DJANGO_DB_PASSWORD` and four `Environment=` lines; `DJANGO_DB_PATH` is dropped. One-off `podman run` commands get the matching `--network`, `--secret` and `-e` flags. `deploy.yaml` checks, before the first change, that the `db.network` file and the secret exist (by name; the value is never read).
14. **Cutover and the migration tool (PD4).** The rehearsal (scratch database `partsdb_rehearsal`) and the real cutover used `migrate`, then `dump_exact`, then `loaddata`, then Django's `sequence_reset_sql`, proven by `data_fingerprint` on both sides (20 rows, identical hash, shown before and after the switch). The first rehearsal **failed** with equal row counts but different hashes: Django's `dumpdata` cuts timestamps to milliseconds while SQLite keeps microseconds. `dump_exact` (a dumpdata with a full-precision encoder, tested) replaces plain `dumpdata`; only the fingerprint made the loss visible. The old SQLite file was moved, not deleted, to `/u01/data/parts-db/legacy-sqlite/` after the owner's checks.
15. **No CREATEDB (PD4).** The `partsdb` role stays `NOCREATEDB` (platform decision, keeps one role to one database). Consequence: `make restore-drill` and the swap of `make restore` cannot run from this repository; they need the platform's `pg-restore-drill` and `pg-restore` (U3). Creating or dropping a scratch database is a platform step.
16. **Where `use_postgres` is set (PD4).** In the ignored `infra/inventory.ini` as a host variable on the `partsdb_rootless` line. `infra/group_vars/all.yml` does not work for this: the group file `partsdb_rootless.yml` (default `false`) takes precedence over `all.yml`.

## Consequences
- Tests asserting the old mount paths and `data_root == service_home/parts-db` change deliberately in PD1.
- The image needs PostgreSQL client tools of major version 17 or newer.
- The `psycopg` driver and `postgresql-client-17` enter the image; its size grows by the client tools.
- `icontains`/`iexact` become locale-aware on PostgreSQL (umlauts match case-insensitively); SQLite only folds ASCII. This is an improvement, but is covered by a test.
